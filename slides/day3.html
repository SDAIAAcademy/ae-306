Dimensional modelling

State the grain in one sentence before anything else

Qafila's grain

One row per line of a confirmed order.

  • Facts are the numbers that add up at that grain: pieces, revenue, cost, freight.
  • Dimensions are what you group and filter by: date, customer, product, supplier.
  • A fact at another grain (freight per shipment) must be brought to this one, or get its own table.

The grain sentence is the test you will write in step 3: no order line twice. Kimball's four steps (business process, grain, dimensions, facts) are the classic source; the order matters, grain before columns.

Transformations as code

One SQL file per model, in git; the dependencies come from the SQL

MODEL (name stg.order_lines, kind FULL, grain (order_id, line_no));

-- the nightly extract re-sent one day's lines: keep one copy of each line
SELECT CAST(order_id AS BIGINT) AS order_id, CAST(line_no AS INTEGER) AS line_no, …
FROM raw.order_lines
QUALIFY row_number() OVER (PARTITION BY order_id, line_no) = 1

Eleven models: six staging, four mart tables, one monthly mart. A review is a diff; a rollback is a revert.

The course uses SQLMesh (0.236 ran here); dbt is the other common choice and its models look almost the same. The difference that matters today is state: SQLMesh knows which version of each model each environment holds, so it can plan.

Tests on data

Four kinds of test cover most of a staging table

Not null

every price has an id

Unique

one row per price id

Accepted values

SAR, USD or AED

Relationships

every product exists

A test is a query returning the rows that break a rule: zero rows passes. One negative cost inserted on purpose trips both the unique and the positive-cost tests.

Severity matters: an error blocks, a warning reports. Decide per test, in the open. Tests are written by the consumer, about its own tables; a contract is the next step.

A data contract

The producer and the consumer agree on the feed, in a file both can read

apiVersion: v3.1.0
kind: DataContract
id: qafila-supplier-prices
schema:
  - name: supplier_prices
    properties:
      - name: cost
        logicalType: string
        required: true
        quality:
          - id: cost_positive_number
            type: sql
            query: SELECT count(*) FROM {object} WHERE num({property}) <= 0
            mustBe: 0

The Open Data Contract Standard (ODCS), maintained by Bitol under the Linux Foundation; version 3.1.0 at the time of writing. Its quality rules use metrics (nullValues, duplicateValues, invalidValues, rowCount) or SQL, with operators such as mustBe and mustBeLessThan. Sources: bitol-io.github.io/open-data-contract-standard. The owner is named in the contract: Ammar Basri. The contract also carries the classification of a field: cost, a supplier's quoted price, is marked restricted before it is loaded, and Day 4 explains the levels.

Checkpoint

Retry or block?

Four failures in last week's runs. Which one should a retry policy handle?

The supplier API timed out after 30 seconds
The contract found a negative cost
A model divides by a column that was renamed
The warehouse disk is full
Why. A retry helps only when a second attempt can succeed with nothing changed. A timeout can; a bad batch, a broken model or a full disk cannot.

Answer: A. Retries on the others hide the failure for a while and delay the alert.

Dagster prints its error log when the check blocks: that is expected, and it is the run log the outcome asks for. If the first run shows no retries, the participant created the API without fail_first. On Colab the first import of Dagster takes about a minute.
