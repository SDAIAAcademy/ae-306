Lab 2.1 · step 2

Follow every page; on a 429, wait and repeat the same request

while True:
    resp = requests.get(f"{base}/prices", params=params, timeout=10)
    if resp.status_code == 429:
        time.sleep(float(resp.headers.get("Retry-After", "1")))
        continue                       # same params: same page
    resp.raise_for_status()
    page = resp.json(); records += page["data"]
    if not page["next_cursor"]:
        break
    params = {"cursor": page["next_cursor"]}

Release 1 of the API: 99 records in five pages; the run met one 429 and made seven requests. Real APIs vary: some page by offset, some by link headers, some return 503 under load. A production client adds a cap on retries and exponential backoff with jitter; say so, the lab keeps it short.

Loads that can run twice

A key and a stored cursor make a load safe to repeat

A key for one record version

(price_id, updated_at), enforced on insert. A version loaded twice is stored once.

The cursor stored with the data

The highest updated_at loaded, in a table of the same database. The next run asks only for what is newer.

Idempotent means running it again changes nothing. Retries, restarts and backfills all depend on it.

Ask why both are needed. The cursor alone: a crash after inserting rows and before saving the cursor re-fetches those rows, and without a key they are inserted twice. The key alone: correct but re-reads the whole API every run.

The failure in between

Store the rows and the cursor in one transaction

Cursor first and a crash loses data silently. Rows first and a crash re-reads, which the key absorbs. Both together and neither can happen.

The stretch of Lab 2.1 kills the load between the two steps and shows that the rollback leaves 99 rows and no new cursor. Object stores have no transactions across files: that is one of the reasons table formats exist (Day 4).

What should a pipeline do with a new column?

Evolve in raw; decide on purpose everywhere after it

evolve

Add the column. Nothing is lost. The default.

freeze

Fail the load. Someone decides.

discard value

Load the row, drop the field.

discard row

Skip the whole record.

The stretch of Lab 2.2 freezes the columns: a record with an unknown field fails the load and the table is unchanged.

These are dlt's four schema-contract modes. Day 3's data contract goes further: it states the columns, types and rules that the producer promises, and a broken promise blocks the mart while raw still records what arrived.

Change data capture, merge and history

03
Change data capture

Read the database's log, not its tables

Supplier tableprocurement edits
→
Write-ahead logevery committed change
→
Change eventsc, u, d with before and after
→
Your copymerged, and history

Polling the table with "changed since" misses deletes and every change between two polls. The log has all of them, in commit order.

Debezium is the common open-source example (on Kafka Connect); managed databases offer their own change streams. The course's feed has Debezium's envelope so the shape transfers: op, before, after, source with the log position, ts_ms.

One change event

The envelope carries the row before, the row after and the log position

{"op": "u",
 "before": {"supplier_id": "S-07", "country": "AE", "currency": "AED", …},
 "after":  {"supplier_id": "S-07", "country": "SA", "currency": "SAR", …},
 "source": {"table": "suppliers", "lsn": 7006317, "ts_ms": 1788242880000},
 "ts_ms": 1788242880298}
  • source.lsn: the order the database committed. ts_ms outside: when the event was sent.
  • A delete has after null; a create has before null.

This is the planted move: Jumeirah Canning (S-07) moves from the UAE to Saudi Arabia on 1 September. Every order before that date belongs to "AE" in finance's question 3, every order after to "SA". The values are the real event from the feed.

Lab 2.3 · step 1

Delivery repeats and reorders; the log position does not

ArrivallsnChange to supplier S-15
117,005,180e-mail becomes accounts6@…
127,004,499payment terms 30 days (older)
137,005,956e-mail becomes accounts7@…

38 events: 3 delivered twice, 1 after a newer change. Applied by arrival, event 12 would put the old e-mail back.

At-least-once delivery is the normal guarantee of change feeds: duplicates are expected, and so is reordering across partitions. Deduplicate on lsn, order by lsn, and the copy never goes backwards.

Lab 2.3 · step 2

MERGE applies the latest change per supplier in one statement

MERGE INTO suppliers AS t USING latest AS s
  ON t.supplier_id = s.sid
WHEN MATCHED AND s.op = 'd' THEN DELETE
WHEN MATCHED THEN UPDATE SET name_en = s.name_en, country = s.country, …
WHEN NOT MATCHED AND s.op <> 'd' THEN INSERT (…) VALUES (…)

18 suppliers, S-12 deleted, S-19 and S-20 created: 19 rows, and EXCEPT both ways against the source finds nothing.

latest is one row per supplier: the highest lsn, which also removes the duplicates. MERGE is in DuckDB since 1.4, and in every warehouse. Reconciliation with the source is the test that matters; without it the copy can drift for months.

History

A type 2 dimension keeps one row per version, with a validity range

suppliercountryvalid_fromvalid_to
S-07AE1 Aug1 Sep
S-07SA1 Sep(current)
S-12TR1 Aug10 Oct (deleted)

52 versions, 19 current, no overlapping ranges. valid_from inclusive, valid_to exclusive: every moment belongs to one version.

Type 1 overwrites (the MERGE copy); type 2 adds a version. A delete ends the last version; nothing is removed, so October orders of S-12 still find their supplier. The test: no two versions of one supplier overlap, and exactly one is current per live supplier.

04
Cleaning with dataframes

A Polars expression is a rule you can name, run and log

RULES = [
  ("digits", "cost_text", pl.col("cost").str.strip_chars()
      .str.replace_many(list("٠١٢٣٤٥٦٧٨٩٫"), list("0123456789."))
      .str.replace(",", ".", literal=True)),
  ("to_sar", "cost_sar", pl.col("cost_text").cast(pl.Float64)
      * pl.col("currency").replace_strict(RATES, return_dtype=pl.Float64)),
]

Polars 2.0 ran for the course. pandas works too; Polars is the example because expressions are values you can store in a list, and because its lazy mode optimises the whole plan (the stretch). DuckDB SQL is the other way to write the same rules.

Checkpoint

Where rounding goes

A price is 61.99 USD per carton of 6. Your colleague converts to riyals, rounds to two decimals, then divides by 6 and rounds again. The ERP shows a different halala. What do you change?

Divide by 6 before converting the currency
Round once, after both steps
Round the ERP's value the same way
Store the cost as a 64-bit float
Why. Currency and unit are both multiplications, so their order does not matter. Rounding in between does: each rounding can move the result by half a unit of the last digit.

Answer: B. The order of conversion is a common debate in the room and the wrong one to have.
