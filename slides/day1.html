Ask the room which column of the table their own organisation's reports run against. The common answer is "the production database, at night": that works until the night gets shorter than the query.

Storage layout

A row store keeps each order together; a column store keeps each field together

Row store (SQLite, PostgreSQL)

One read returns a whole order line. An index on order_id finds it without scanning. Summing one field reads every field.

Column store (DuckDB, warehouses)

A sum reads only qty, unit_price_sar and discount_pct, compressed and in batches. Fetching one whole row touches every column file.

Draw the same four order lines twice on the board: once as rows, once as columns. Circle what a monthly sum reads in each. Then what a lookup of one order reads.

ELT

Copy first, transform where the analysis runs

Extractnightly copy of orders
→
Loadunchanged, into raw
→
TransformSQL in the analytical engine
  • Loading before transforming keeps the evidence: a wrong rule can be fixed and re-run on the raw copy.
  • The transformation runs on the engine built for scans, not on the order database.

ETL transformed before loading because storage was expensive. With cheap storage the order flipped. Qafila's old report is ETL in a spreadsheet: the raw data is gone after the macro runs, so nobody can say where a number came from.

Layered refinement

Raw, staging and marts: each layer has one job

Raw

Exactly as received, dated, never edited. The extracts, the API pages, the change feed.

Staging

Typed, deduplicated, one row per key. One model per source table.

Marts

Facts and dimensions that answer finance's questions. Tested.

Some teams call them bronze, silver and gold. The names matter less than the rule: each layer reads only the one before.

Point forward: Lab 1.2 works on raw, Day 2 builds staging, Day 3 builds the marts. Ask what goes wrong when a mart reads raw directly: every mart re-implements the deduplication, differently.

An analytical engine in your notebook

DuckDB runs inside Python and reads files where they are

import duckdb
con = duckdb.connect()
con.sql("""
  SELECT status, count(*) AS orders
  FROM read_csv('data/raw/extracts/orders.csv')
  GROUP BY ALL""")

No server, no load step: a CSV, Parquet or JSON file is a table. The same SQL later runs on a warehouse.

Other in-process engines: Polars (SQL and dataframes, Day 2), chDB, DataFusion. DuckDB is the course's default because its SQL is close to the warehouses' and it reads every format we use. Show SUMMARIZE live: one line profiles a whole file.

Count before and after every join. A join that changes the count without a reason you can state is a defect.

Cost at the right price

Join each line to the price valid on its order date

JOIN read_csv('prices.csv') AS pr
  ON pr.product_id = l.product_id
 AND o.order_date BETWEEN pr.valid_from
                     AND coalesce(pr.valid_to, DATE '9999-12-31')
  • 58 products, 102 price versions: prices changed inside the quarter.
  • Costing with today's price moves last month's margin every time procurement updates a price.
  • Cartons become pieces first: qty * units_per_carton.

The open end (valid_to empty) is the current price. Ask why BETWEEN is safe here: the ERP's ranges do not overlap and valid_to is inclusive. Day 2's type 2 dimension uses an exclusive end instead; say that both conventions exist and the model must state which.

03
GROUP BY and OVER

GROUP BY collapses rows; a window keeps them and adds a value

SELECT order_date, sum(revenue)
FROM mart.fct_order_line
GROUP BY order_date
SELECT order_id, revenue,
  sum(revenue) OVER (
    PARTITION BY order_date)
FROM mart.fct_order_line

One September week: 7 rows on the left, 1,228 on the right, each with its day's total beside it.

From Lab 1.3 step 1. The window answers "this line's share of its day" without a self-join. Ask for another question that needs the row and the group together: each customer's order against the customer's average.

Three parts of OVER

Partition says where it restarts, order says what "so far" means

sum(margin) OVER (
  PARTITION BY month              -- restart each month
  ORDER BY order_date             -- "so far" in date order
  ROWS BETWEEN UNBOUNDED PRECEDING
           AND CURRENT ROW)        -- the frame

The last day of each month equals finance's monthly margin: 5,413,128 riyals for August.

Without ROWS, an ORDER BY window uses RANGE: rows that tie on the order key are summed together. With one row per day it makes no difference; with lines it does. Say it once; the stretch of Lab 1.3 shows ties.

One row per group

ROW_NUMBER and QUALIFY keep the first or last row of each group

SELECT * FROM stg.orders
QUALIFY row_number() OVER (
  PARTITION BY customer_id ORDER BY created_at DESC) = 1
  • The same pattern deduplicates the re-sent lines of Lab 1.2 and picks the latest change event on Day 2.
  • Windows run after WHERE, so WHERE cannot filter them; QUALIFY can.

QUALIFY exists in DuckDB, Snowflake, BigQuery and Databricks; elsewhere wrap the query and filter outside. arg_min and arg_max are a shorter alternative for "the id at the earliest date".

17,665

A predicate on the partition you know changed (order_date >= DATE '2026-10-01') turns a rebuild into an update. The result must equal the full recompute: test that.

From the stretch of Lab 1.2. Windows complicate this: a running total for October needs nothing before October because it restarts each month, but a running total since the start of the year would need the last value of September. State what the window reads before making it incremental.

Checkpoint

A running total that never resets

Your margin-to-date keeps growing across August, September and October instead of restarting on the first of each month. What is missing?

PARTITION BY month in the window
ORDER BY month instead of order_date
A GROUP BY month around the query
ROWS BETWEEN 30 PRECEDING AND CURRENT ROW
Why. The partition decides where a window starts again. Without it the whole table is one partition, so the total runs from the first day to the last.

Answer: A. The 30-row frame is a tempting wrong answer: it produces a moving 30-day sum, a different measure that only looks like a reset.

Inside a Parquet file

Each row group keeps the minimum and maximum of every column

  • A reader checks the footer first and skips the row groups whose range cannot match the filter.
  • Shuffled rows: every group spans every date, so nothing is skipped.
  • Sorted rows: each group covers a few days.
RowsGroups that may hold 14 Sep
shuffled7 of 7
sorted by date2 of 15

Show parquet_metadata live: one row per row group and column with stats_min and stats_max. Sorting on write is free compared with what it saves on every read that filters on that column.

Partitioning

A folder per month lets the reader skip whole files

COPY big TO 'by_month' (FORMAT parquet, PARTITION_BY (month));
-- by_month/month=2026-08/…  month=2026-09/…  month=2026-10/…
SELECT … FROM read_parquet('by_month/*/*.parquet', hive_partitioning = true)
WHERE month = '2026-09'      -- Scanning Files: 1/3

The September query reads 2.8 MB of 9.6 MB. At this size the time hardly changes; on object storage the bytes are the bill.

Be honest about the measurement: locally, 23 ms against 27 ms is noise. Pruning pays when the data is large or remote. The plan line "Scanning Files: 1/3" is the proof, from the stretch of Lab 1.4.

The opposite mistake

Partition by day and customer and a full scan is 180 times slower

3,841
files, most under a kilobyte
15 ms → 2,725 ms
one file against all of them

Every file has a footer to open and a request to make. Partition on a column that queries filter by and that has few values.

Streaming and frequent small appends make small files too; table formats answer with compaction, which Day 4 shows. Ask: which Qafila column would you partition the order lines by? Month, and nothing else at this size.

Checkpoint

The query that reads everything

The lines are partitioned by month, yet a query for September still scans all three folders. The filter is WHERE strftime(order_date, '%Y-%m') = '2026-09'. Why?

Parquet cannot prune folders
The row groups are not sorted
Three folders are too few to prune
The filter is on order_date, not on the partition column month
Why. The reader prunes folders by the partition column's value. A filter on another column, even one that implies the month, cannot be matched to folder names.

Answer: D. Fix: filter on month = '2026-09', or partition by a column the queries already use. Table formats (Day 4) solve this with hidden partitioning: the table knows month is derived from order_date.
